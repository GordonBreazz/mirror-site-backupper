# mirror-site-backupper

Bash-скрипт для бэкапа сайтов и баз данных с виртуального хостинга через `rsync` и `mysqldump`.

## Ключевая идея

Все SSH-операции за один прогон скрипта идут через **одно** мультиплексированное
SSH-соединение (`ControlMaster`/`ControlPersist`) — вместо того, чтобы открывать
новое подключение на каждую базу данных или файловую операцию. Это устраняет
проблему бана по количеству SSH-соединений на стороне хостинга.

## Что делает скрипт

1. Открывает одно управляющее SSH-соединение на весь прогон.
2. Дампит все базы данных одним удалённым сеансом (один `ssh`-вызов, скрипт
   на удалённой стороне сам проходит по всем базам из `DATABASES[]`).
3. Копирует корень сайтов (файлы + дампы БД, они лежат внутри того же корня)
   одним `rsync`-вызовом на локальную машину.
4. Сохраняет список изменённых за этот прогон файлов
   (`logs/changed_files_<дата>.log`) — на основе `rsync --itemize-changes`,
   без дополнительной логики сравнения.

## Чего скрипт **намеренно не делает**

Тяжёлая пост-обработка (антивирус-проверка, оптимизация изображений,
git-версионирование кода) сюда не входит — она должна быть отдельным,
независимым пайплайном, который читает готовый результат бэкапа
(`site-mirror/` + `changed_files_<дата>.log`) и не может повлиять на
надёжность самого бэкапа, если упадёт или не уложится в ресурсы.

## Структура проекта

```
backup.sh              # главный скрипт
install.sh                    # интерактивная настройка credentials.conf
functions/
├── logging.sh                 # log() / log_error()
├── connection.sh               # SSH ControlMaster: open/close/remote_ssh
├── databases_dump_create.sh    # дамп всех БД одним удалённым сеансом
└── rsync_files_copy.sh         # копирование файлов + список изменений
credentials.conf.example       # пример конфига — скопируйте в credentials.conf
deploy/
└── mirror-site-backupper.logrotate  # ротация логов (см. раздел "Ротация логов")
```

## Настройка

1. Склонируйте репозиторий:
   ```bash
   git clone https://github.com/GordonBreazz/mirror-site-backupper.git
   cd mirror-site-backupper
   chmod +x backup.sh install.sh
   ```

2. Настройте `credentials.conf` — двумя способами на выбор:

   **А) Автоматически, через установщик** (спросит параметры подключения,
   поможет создать/скопировать SSH-ключ, соберёт список баз данных):
   ```bash
   ./install.sh
   ```

   **Б) Вручную**, скопировав пример и отредактировав:
   ```bash
   cp credentials.conf.example credentials.conf
   nano credentials.conf
   ```
   Понадобится: `REMOTE_USER`, `REMOTE_HOST`, `REMOTE_ROOT_DIR` (корень со
   всеми сайтами хостинга) и список баз данных в `DATABASES[]`.
   `SSH_KEY_PATH` указывать не обязательно — если в `~/.ssh` только один
   ключ, скрипт найдёт его сам.

3. Проверьте локальные пути в начале `backup.sh` — это **обязательный шаг**,
   не пропускайте его:
   ```bash
   nano backup.sh
   ```
   Параметры в блоке настроек (`БЛОК НАСТРОЕК СКРИПТА`):
   - `LOCAL_DIR_PATH` — корень для бэкапов. По умолчанию `"$HOME/backup"`
     (домашняя папка текущего пользователя) — работает "из коробки" для
     любого пользователя без правки, но при желании можно указать любой
     другой путь, например `/mnt/backups`.
   - `NAME_LOCAL_DIR`, `NAME_MIRROR_DIR`, `NAME_LOGS_DIR` — названия
     подпапок внутри `LOCAL_DIR_PATH` (зеркало сайтов, логи). Менять не
     обязательно, но можно под свои привычки.

4. Убедитесь, что на локальной машине установлен `rsync`:
   ```bash
   sudo apt install -y rsync
   ```

## Запуск

Сделайте файл скрипта исполняемым (если ещё не сделали на шаге 1):

```bash
chmod u+x backup.sh
```

Запустите скрипт:

```bash
bash backup.sh
```

либо

```bash
./backup.sh
```

Скрипт выполнит следующие действия:

- Откроет одно управляющее SSH-соединение к серверу (переиспользуется для
  всех следующих шагов).
- Создаст дампы всех указанных баз данных одним удалённым сеансом и
  сохранит их в подпапке внутри `REMOTE_ROOT_DIR` на сервере.
- Скопирует одним `rsync`-вызовом файлы сайтов и дампы баз данных с сервера
  на локальную машину.
- Сохранит список изменённых за этот прогон файлов в `logs/`.

### Ожидаемый результат

После завершения работы скрипта вы получите:

```
$LOCAL_DIR_PATH/$NAME_LOCAL_DIR/
├── site-mirror/          # зеркало всех сайтов + дампы БД
└── logs/
    ├── backup.log                    # общий лог прогона
    ├── backup_error.log              # только ошибки
    ├── rsync.log                     # технический лог rsync
    └── changed_files_<дата>.log      # что изменилось в этом прогоне
```

## Автоматизация через cron

```bash
crontab -e
```

```
0 5 * * * flock -n /tmp/backup_script.lock /путь/к/mirror-site-backupper/backup.sh >> /путь/к/cron.log 2>&1
```

`flock -n` не даёт запуститься второй копии скрипта, если предыдущий прогон
ещё не завершился к моменту следующего срабатывания cron.

### Несколько аккаунтов на одном сервере

Если бэкапите несколько хостинг-аккаунтов с одного сервера — держите для
каждого свою папку с отдельным клоном репозитория и своим `credentials.conf`,
например:
```
~/backup/timeweb/mirror-site-backupper/
~/backup/другой-хостинг/mirror-site-backupper/
```
У каждой — своя строка в `crontab -e` и свой `production-backup/`.

## Ротация логов

Два вида логов растут бесконечно, если их не ограничивать:
- `cron.log` (если настроили вывод cron в файл, см. выше) — дописывается
  каждый день;
- `production-backup/logs/changed_files_<дата>.log` — новый файл на
  каждый прогон.

(Логи в `production-backup/logs/backup.log`, `backup_error.log`, `rsync.log`
сюда не входят — они перезаписываются заново при каждом запуске, расти
бесконечно не могут.)

Установите готовую конфигурацию `logrotate` (одна маска покрывает сразу
все аккаунты вида `~/backup/*/...`, добавлять новый аккаунт в конфиг
отдельно не нужно):

```bash
sudo cp deploy/mirror-site-backupper.logrotate /etc/logrotate.d/mirror-site-backupper
sudo logrotate -d /etc/logrotate.d/mirror-site-backupper   # проверка без реальных действий
```

`logrotate` на Debian уже установлен и запускается сам через системный
`/etc/cron.daily/logrotate` — больше ничего настраивать не нужно.

⚠️ Пути внутри `deploy/mirror-site-backupper.logrotate` (`/home/nix/backup/*/...`)
рассчитаны на структуру `~/backup/<аккаунт>/...` под пользователем `nix`.
Если у вас другой пользователь или другая корневая папка — поправьте пути
в файле перед установкой.

## Безопасность

- `credentials.conf` содержит пароли БД в открытом виде — файл добавлен в
  `.gitignore`, никогда не коммитьте его.
- Ограничьте права на сам скрипт и конфиг:
  ```bash
  chmod 700 backup_script.sh
  chmod 600 credentials.conf
  ```
- Резервные копии на диске не шифруются — при необходимости добавьте
  шифрование отдельным шагом после `backup.sh`.
